# DB 락 전략 실험 (lock-service)

쇼핑몰 주문으로 "같은 재고를 동시에 건드릴 때" 생기는 문제를 재현하고, 락 전략과 데드락 방지책을 비교한다.
화면: 왼쪽 메뉴 DB > "DB 락 전략". 서비스: `lock-service`(9209), 실행은 `scripts/run-backend.sh lock`.

## 1. 왜 하는가
- 주문이 몰릴 때만 초과 판매, 재고 어긋남, 데드락이 생긴다. 평소 테스트에서는 안 보여서 직접 재현해 봐야 감이 생긴다.
- "락을 쓰면 된다"에서 끝나지 않는다. 방법마다 대가가 다르고(기다림, 재시도), 락을 쓰면 데드락이 따라온다.
- 락을 잡은 채 외부 호출(결제)을 하면 처리량이 어떻게 무너지는지 숫자로 확인한다.

## 2. 구성
| 항목 | 내용 |
|---|---|
| 테이블 | `lock_product`(재고, 버전), `lock_order`, `lock_order_item`. 서비스가 시작할 때 `schema.sql`로 만든다(있으면 그대로). |
| 실행 방식 | 주문자를 스레드로 흉내 낸다. 모든 스레드를 대기시킨 뒤 한꺼번에 출발시킨다(최대 동시 50). |
| 트랜잭션 | `@Transactional` 없이 JDBC 로 직접 다룬다. 락이 잡히고 풀리는 시점이 코드에 그대로 보이게 하려는 것이다. 격리 수준은 MariaDB 기본값(REPEATABLE READ). |
| 검증 | 끝난 뒤 DB 에 남은 값으로 확인한다: 처음 재고 − 팔린 수량 = 남은 재고, 재고 ≥ 0, DB 의 주문 수 = 성공 수. 앱의 카운터는 믿지 않는다. |
| 안전장치 | 락 대기는 5초가 넘으면 오류로 끝난다(`innodb_lock_wait_timeout=5`). 한 번에 하나만 실행한다(다른 요청은 409). 매 실행 전에 상품과 주문을 처음 상태로 되돌린다. |
| 결과 | `test_result`(`test_type = lock-lab`)에 저장되어 새로고침해도 남는다. |

## 3. 실험 9가지
### 재고 차감 (재고 10, 주문 100건)
| id | 방식 | 코드 |
|---|---|---|
| `stock-none` | 락 없음 | `SELECT stock` → 앱에서 계산 → `UPDATE SET stock=?`(읽은 값으로 덮어쓴다) |
| `stock-atomic` | 원자적 UPDATE | `UPDATE SET stock=stock-1 WHERE id=1 AND stock>=1`, 영향 행이 0이면 품절 |
| `stock-pessimistic` | 비관적 락 | `SELECT … FOR UPDATE` → `UPDATE SET stock=stock-1` |
| `stock-optimistic` | 낙관적 락 | `SELECT stock, version` → `UPDATE … WHERE version=?`, 영향 행 0이면 다시(최대 10번, 1~7ms 흩어서) |

### 데드락 (상품 2개를 한 주문에, 주문 20건)
| id | 방식 | 설명 |
|---|---|---|
| `deadlock-cross` | 서로 다른 순서 | 짝수 주문은 상품 1→2, 홀수 주문은 2→1 순서로 `FOR UPDATE`. 첫 상품을 잠근 뒤 10ms 쉰다. |
| `deadlock-ordered` | 순서 통일 | 모든 주문이 1→2 순서 |
| `deadlock-retry` | 다시 시도 | 순서는 `cross` 와 같게 두고, 오류 1213 을 받으면 롤백 후 처음부터(최대 5번, 5~30ms 쉬고) |

"10ms 쉼"은 실제 주문에서 가격 계산, 쿠폰 확인 같은 일이 두 락 사이에 끼는 것을 흉내 낸 것이다. 이 틈이 없으면 두 요청이 우연히 겹쳐야만 데드락이 나서 재현이 들쭉날쭉해진다.

### 트랜잭션 길이 (상품 1개, 주문 50건, 결제 20ms)
| id | 방식 | 설명 |
|---|---|---|
| `tx-long` | 결제를 안에서 | `FOR UPDATE` 로 잠근 채 결제(20ms 대기)를 하고 차감 |
| `tx-short` | 결제를 밖에서 | 결제는 동시에 하고, 원자적 UPDATE 로 짧게 차감 |

## 5. 읽는 법
- **락 없음**: 100건이 모두 "성공"했고 재고는 7이 남았다. 팔린 수량(100)을 재고(10)에서 빼면 −90이어야 하는데 7인 것이 갱신 손실이다. 50개 스레드가 모두 재고 10을 읽고 각자 9를 써 넣은 결과다. 재고가 음수가 되지 않아서 눈에 안 띄는 점이 위험하다(돈은 나갔는데 재고는 남아 있다).
- **락 3가지**: 모두 10건만 팔고 재고가 맞는다. 시간은 모두 수십 ms 로 이 규모에서는 차이가 의미 없다(연결 풀은 실험 전에 미리 데워서, 연결을 만드는 시간은 재지 않는다). 차이는 성격에 있다. 원자적 UPDATE 는 SQL 한 문장이라 가장 단순하다. 비관적 락은 줄을 세운다(읽는 순간부터 잠긴다). 낙관적 락은 잠그지 않는 대신 부딪힐 때마다 다시 하며, 이 조건에서 재시도가 약 200번 나왔다. 충돌이 잦은 곳(인기 상품)에서는 낙관적 락이 불리하다.
- **데드락**: 20건 중 10건이 DB 에 의해 취소됐다. 재고는 맞지만 손님은 주문에 실패한 것이다. 서버가 멈추지는 않는다(DB 가 한쪽을 골라 취소하면 나머지가 이어서 끝난다).
- **순서 통일 vs 다시 시도**: 순서를 맞추면 데드락이 없고 20건이 모두 성공한다. 다시 시도는 데드락을 없애지 못한다. 같은 순서로 다시 들어가면 또 부딪히므로 밀려난 주문 일부(6~9건)는 5번을 다 써도 실패했다. 순서 통일이 시간이 더 길어 보이는 것은 20건을 모두 끝냈기 때문이다(`cross` 는 절반을 취소해서 일이 적었다).
- **트랜잭션 길이**: 결제를 안에서 하면 총 시간이 주문 수 × 결제 시간(50 × 20ms ≈ 1초)에 가깝다. 밖에서 하면 결제가 동시에 진행되어 한 자릿수 배 이상 짧다.

## 6. 주의와 한계
- 시간과 재시도 횟수는 돌릴 때마다 달라진다. 갱신 손실의 정확한 값(남은 재고 7)도 타이밍에 따라 바뀔 수 있다. 초과 판매가 생긴다는 점과 어긋남 판정이 이 실험의 결론이다.
- 주문 스레드와 DB 가 같은 PC 에 있어서 네트워크 지연이 없다. 실제 환경에서는 왕복 시간이 락 보유 시간을 늘려 결과가 더 나빠진다.
- 결제를 밖에서 하면 재고가 없을 때 결제를 취소(환불)해야 한다. 실제로는 "재고를 먼저 잡아 두고(예약) 결제하고 확정"하는 식으로 설계한다. 이 실험은 락 보유 시간만 본다.
- 락 대기 5초는 실험이 멈추지 않게 둔 값이다. 운영 값(기본 50초)과 다르다. 결제를 안에서 하는 실험에서 결제 시간 100ms, 주문 50건 이상이면 줄 끝의 주문이 5초(약 49 × 100ms) 가까이 기다려 `대기 초과`로 실패할 수 있다(그것도 관찰 대상이다).
- MariaDB(InnoDB) REPEATABLE READ 기준이다. 격리 수준, DB 종류가 다르면 락 범위(갭 락 등)와 오류 번호가 달라질 수 있다.
- 쿠폰 선착순, 분산 락(Redis), 큐로 직렬화하는 방법은 다루지 않았다.

## 7. 다음에 해 볼 것
- 격리 수준을 READ COMMITTED 로 바꿔 갱신 손실과 갭 락이 어떻게 달라지는지
- 같은 실험을 Redis 분산 락(Redisson)과 비교
- 재고 예약(선점) 후 결제하는 설계로 `결제를 밖에서`의 환불 문제 해결
