# 수박 게임 만들기 (Canvas + 직접 구현한 2D 물리)

"같은 공끼리 붙이면 다음 단계로 합쳐지는" 수박 게임을 이미지 없이 원(circle)만 그려서 만든 기록.
물리 엔진 라이브러리를 쓰지 않고 충돌·마찰·회전을 직접 구현했다. 화면은 `frontend`의 `수박 게임` 메뉴(`/#/suika`).

> 스터디용으로 만든 것이라, 코드보다 **왜 그렇게 했는지**와 **막혔던 점**을 중심으로 적는다.
> 화면 안의 "동작 원리"/"조작·규칙" 카드에도 항목별로 번호 붙은 설명과 코드가 들어 있다(`game/impl.ts`).

## 1. 구성

| 파일 | 역할 |
|---|---|
| `src/game/suika.ts` | 게임 엔진. 물리·합치기·효과·게임 오버·최고 점수. Vue를 모른다 |
| `src/views/SuikaView.vue` | 화면. 캔버스, 점수 패널, 입력 연결, 설명 카드 |
| `src/components/BallIcon.vue` | 패널의 작은 공 아이콘(판의 공과 같은 `drawBall()`로 그린다) |
| `src/components/StepList.vue` | "동작 원리"/"조작·규칙"의 아코디언(번호 설명 + 코드) |
| `src/game/impl.ts` | 아코디언에 보여 줄 설명과 코드 복사본 |
| `src/style.css` | 공 색 토큰 `--fruit-1~11`, `--ball-shine`, `--game-overlay*` (라이트/다크) |

**엔진과 화면을 나눈 이유**: 엔진은 `canvas`와 콜백(`onChange`) 하나만 받는다. 화면은 점수 같은 값이 바뀔 때만 콜백으로 알림을 받아 Vue 상태에 복사한다.
물리는 매 프레임 수십 개 객체가 바뀌므로 Vue 반응형으로 두지 않고, 엔진 안의 평범한 객체로 둔다.

## 2. 핵심 개념

### 2-1. 이미지 없이 그리기
- `ctx.arc()`로 원을 채우고, 반투명 흰 원을 왼쪽 위로 비껴 하나 더 그려 입체감을 낸다.
- 색은 CSS 변수(`--fruit-N`)를 `getComputedStyle`로 읽어 쓴다. 라이트/다크 테마가 자동으로 따라오고 프로젝트 규칙(색은 CSS 토큰만)도 지킨다.
- 하이라이트를 **공의 회전 각도만큼 같이 돌려** 그리면 별도 표시 없이 구르는 게 보인다(처음에는 검은 점을 따로 그렸다가 하이라이트로 바꿨다).
- 화면 배율(`devicePixelRatio`)만큼 캔버스 해상도를 키우고 좌표계는 360×520으로 유지한다.

### 2-2. 게임 루프: 고정 타임스텝
```ts
this.acc += Math.min(t - this.last, 100)      // 경과 시간 누적(최대 100ms)
while (this.acc >= 1000 / 60) { this.step(); this.acc -= 1000 / 60 }
this.draw()
```
- 그리기는 `requestAnimationFrame`마다, 물리는 **1/60초 단위로 정확히 N번** 진행한다.
- 모니터가 144Hz여도 프레임이 끊겨도 게임 속도가 같다. 탭을 오래 비워도 100ms로 잘라 한 번에 쏟아지지 않게 한다.

### 2-3. 이동과 벽·바닥
- `vy += 0.35`(중력), `x += vx`. 가로 속도는 프레임마다 0.5%씩 줄인다(공기 저항).
- 벽·바닥은 위치를 경계로 되돌리고 **벽으로 향하는 속도일 때만** 반대로 뒤집되 일부만 남긴다(반발 계수 0.2).

### 2-4. 원끼리 충돌 (위치 보정 + 충격량)
1. **겹침 판정**: 중심 거리 < 반지름 합. 제곱 값으로 먼저 비교해 제곱근 계산을 아낀다.
2. **위치 보정**: 겹친 만큼을 **질량 반비례**로 나눠 서로 반대로 민다. 질량은 반지름²(원의 넓이에 비례).
3. **속도 보정**: 서로 다가오는 중일 때만 충격량 `imp = -(1+e)·rv / (1/ma + 1/mb)`를 두 공에 질량 반비례로 나눈다. 반발 계수 e는 기본 0.1.
4. **반복**: 한 프레임에 이 과정을 4번 돌린다. 한 번만 하면 쌓인 공이 서로 파고들거나 떤다. 반복할수록 밀어낸 결과가 이웃에게 전파되어 안정된다(비용은 4배).

### 2-5. 회전과 마찰 (구르기)
- 공마다 `angle`(각도)과 `w`(각속도)를 가진다.
- 접촉점에서 두 표면이 미끄러지는 속도 `vt = (vb−va)·t − rb·wb − ra·wa`를 구하고, 이걸 없애는 마찰 충격량 `jt`를 계산한다. 단 **누르는 힘의 0.4배를 넘지 못한다**(쿨롱 마찰).
- `jt`는 접선 방향 속도를 바꾸는 동시에 공을 돌린다. 원판의 관성모멘트 `½mr²` 때문에 회전 변화량은 `2·jt/(m·r)`이고, 질량이 반지름²이라 분모가 `3·(1/ma + 1/mb)`로 정리된다.
- 벽·바닥도 같은 원리로, 미끄러짐을 줄인 만큼(`dv`) 회전(`2·dv/r`)을 만든다. 바닥에는 구름 저항(×0.985)을 둔다.

### 2-6. 합치기, 점수, 게임 오버
- 충돌 처리가 끝난 **뒤에** 같은 단계 쌍을 찾는다(거리 ≤ 반지름 합 + 0.5). 두 공을 지우고 중간 위치에 한 단계 큰 공을 만든다(속도·회전은 평균).
- 점수는 합치기 전 단계 값: `1, 3, 6, 10, 15, 21, 28, 36, 45, 55, 66`. 가장 큰 공끼리 만나면 새 공 없이 사라지고 +100.
- 게임 오버: 생긴 지 1초(60프레임) 넘은 공이 점선 위에 **2초(120프레임) 연속** 걸쳐 있으면 끝. 막 떨어지는 공은 `age`로 제외한다.
- 새 공은 0~4단계(작은 5종) 중 무작위. 큰 공은 합쳐야만 만들 수 있다.

### 2-7. 효과 (파티클)
- 합칠 때 링 1개, 불꽃 10개, 떠오르는 `+점수`를 **효과 목록**에 넣는다. 공과 별개 목록이라 물리에 영향이 없고, 물리와 같은 1/60초 단위로 수명(`life`)을 줄여 0이 되면 지운다.
- 새 공은 `pop` 카운터(12프레임) 동안 **그림만** 최대 18% 크게 그린다(충돌 반지름은 그대로).
- 게임이 끝나도 효과는 끝까지 재생한다(`step()` 맨 앞에서 먼저 갱신).

### 2-8. 최고 점수 저장 (localStorage)
- 키 `note.suika.best`. 점수가 최고를 넘는 순간에만 저장하고, 저장할 때 **저장된 값과 비교해 큰 쪽**을 남긴다(탭을 여러 개 열었을 때 높은 점수를 덮어쓰지 않도록).
- 읽기·쓰기를 `try/catch`로 감싼다. 시크릿 모드나 차단 환경에서도 게임이 멈추지 않는다(이때는 새로고침하면 0부터).

### 2-9. 입력
- 포인터 위치를 `getBoundingClientRect` 비율로 판 좌표(360)로 환산하고, 공 반지름만큼 안쪽으로 제한한다.
- 투하: **왼쪽 버튼을 판에서 눌렀다가 판에서 뗄 때**(`pressed` 플래그) 또는 스페이스바. 쿨다운 30프레임(0.5초).
- 스페이스바는 판이 화면에 보일 때만, 키 반복·조합키가 아닐 때만, 입력 요소에 포커스가 없을 때만 동작한다.

## 3. 만든 순서

1. **기존 규칙 확인** — `CLAUDE.md`의 화면 포맷(카드, 푸터 옵션, 불릿 설명, PageNav, CSS 토큰)과 `BulkInsertView.vue`를 기준으로 삼았다. 메뉴(`menu.ts`)와 라우터(`router.ts`)에 항목을 추가했다.
2. **엔진 첫 버전** — 중력, 벽·바닥, 원끼리 충돌, 합치기, 게임 오버를 한 파일에 구현. 처음에는 "이미지가 없으니 원을 그린다"가 전제였다.
3. **화면** — 캔버스 + 점수 패널. 과일 이름과 단계 숫자는 지우고 색만으로 구분했다.
4. **옵션/물리 개선** — `튕기기` 옵션(반발 계수 0.55/0.6), 회전과 마찰, 정중앙 균형 깨기.
5. **덧붙인 기능** — 최고 점수 저장, 합칠 때 효과, 단계별 만든 횟수.
6. **설명 카드** — "동작 원리"/"조작·규칙"을 항목별 아코디언으로 만들고, 설명의 번호(①②③)와 코드 주석의 번호(`1)`,`2)`)를 짝지었다.
7. **리뷰 반복** — 먼저 아이콘 부분만 리뷰했고(8건), 이어서 수박 게임 전체 코드를 대상으로 코드 리뷰 → 수정 → 재리뷰를 5회 돌렸다(지적 16·8·6·6·3건). 마지막 회차에는 재현되는 버그가 없어서 멈췄고, 남은 3건은 취향 수준이라 고치지 않았다.

## 5. 막혔던 점

- **정중앙에 얹힌 공이 안 떨어진다** — 접촉 힘이 완전히 수직이면 좌우로 밀 힘이 없어 영원히 균형을 잡는다. 현실에서는 불안정 평형이라 흔들림으로 깨진다. 겹친 두 공의 x 차이가 0.05 미만이면 **위쪽 공을 0.5px 밀어** 대칭을 깼다. 마우스를 안 움직이고 스페이스로 연속 투하하면 실제로 생기는 상황이다.
- **클래스 이름 충돌** — 오른쪽 패널에 쓴 `.side`가 왼쪽 메뉴용 전역 `.side`(`position: sticky; height: 100vh; border-right`)와 겹쳐 이상한 세로선이 생겼다. `.panel`로 바꿨다. scoped 스타일이어도 **전역 스타일은 그대로 적용된다**.
- **카드를 접으면 NaN** — 접힌 카드는 `display:none`이라 캔버스 폭이 0이다. `((clientX − left) / width) * W`가 `0/0`이 되어 `aimX`가 NaN이 되고, 그 좌표로 공이 투하되면 충돌 계산이 이웃 공까지 NaN으로 오염시킨다. 폭이 0이면 계산하지 않고, 투하 후에는 화면 좌표를 거치지 않고 `aimX`를 직접 보정한다.
- **벽 반발이 방향을 안 봤다** — 이웃이 밀어서 벽 쪽으로 눌린 공이 벽에서 멀어지는 중인데도 속도를 뒤집어 다시 벽으로 보냈다. 이제 벽으로 향할 때만 반사한다. 충돌 계산 마지막에 위치를 판 안으로 되돌리고 안쪽 속도도 0으로 만든다.
- **스페이스바와 포커스** — 버튼을 클릭한 뒤 포커스가 남으면 스페이스가 그 버튼을 다시 누른다(`새 게임`이 초기화, 카드 머리글이 접힘). 마우스로 누른 뒤에만 포커스를 풀고(`click`의 `detail === 0`이면 키보드라서 유지), 이 페이지 안의 클릭에만 적용한다.
- **생성 중 콜백** — 엔진 생성자 안에서 호출된 `onChange`는 `game` 변수 대입 전이라 건너뛴다. 저장된 최고 점수가 화면에 안 나와서 생성 직후 `sync()`를 한 번 더 불렀다.
- **개발 서버와 localStorage 차단** — 저장소를 막은 채 개발 서버로 열면 pinia 개발용 코드가 먼저 터진다(프로덕션 빌드에는 없는 코드). 차단 시나리오는 프로덕션 빌드(`vite preview`)로 확인했다.
- **설명 복사본 불일치** — 화면에 보여 주는 코드(`impl.ts`)는 실제 코드의 복사본이라 코드를 고칠 때마다 어긋났다. 리뷰에서 가장 자주 나온 지적이다. 지금은 사람이 같이 고쳐야 한다.

## 6. 검증 방법 메모
- **Playwright**: 개발 서버의 Vue 내부(`canvas.__vueParentComponent.setupState.game`)로 엔진 객체를 잡아 공을 직접 넣고 값을 측정했다. 프로덕션 빌드에서는 이 경로가 없어 마우스로 실제 플레이했다.
- 마우스/키보드 시나리오(오른쪽 클릭, 판 밖에서 누르고 판에서 뗌, 반복 키, 조합키, 접힌 카드, 포커스)는 `dispatchEvent`와 실제 `mouse`/`keyboard`를 섞어 확인했다.
- 한계: Chromium에서만 확인했다(Firefox/Safari 미확인).

## 7. 알려진 한계와 더 해볼 것
- 키보드만으로는 조준·투하할 수 없다(마우스/터치 게임). 하려면 캔버스에 포커스를 주고 방향키를 설계해야 한다.
- 브라우저 확대나 모니터 이동으로 DPR이 바뀌면 캔버스 해상도가 갱신되지 않는다.
- 공 쌍 비교가 O(n²)이다. 수백 개가 되면 격자(공간 분할)로 이웃만 비교해야 한다.
- 서브스텝을 늘리거나 위치 기반 동역학(PBD)으로 바꾸면 더 안정되지만 이 판 크기에서는 지금도 충분하다.
- 합칠 때 효과음, 모바일 터치 조준 보정, 최고 점수 초기화 버튼.

## 8. 결론

### 내 소감
- 수식이 가장 고민이었다. 내 능력 밖의 문제였던 것 같다.
- 게임이 단순해도 시나리오별로 계산하는 부분이 생각보다 많았다.
- 가장 궁금했던 건 원과 원의 충돌을 어떻게 계산하느냐였다. 단계별 설명은 2-4번과 화면의 "동작 원리 > 충돌"에 있다.
- AI 없이는 하기 힘든 작업임을 느꼈다.

### AI(Claude)의 소감
- 수식 자체는 강체 충돌의 표준 공식(겹침 판정, 위치 보정, 충격량, 쿨롱 마찰)을 2D 원에 맞춘 것이라 새로 만들어 낼 건 없었다. 어려운 쪽은 이걸 한꺼번에 돌렸을 때 공이 안정적으로 쌓이게 만드는 일이었다.
- 공식보다 시간을 더 쓴 건 안정적으로 보이게 하는 보정이었다. 낮은 반발 계수, 느린 속도는 정지, 충돌 4번 반복, 정중앙 균형 깨기.
- "1번 공 위에 4번 공을 떨어뜨리면 굴러 떨어지지 않나?"라는 질문이 가장 값졌다. 실제로 정중앙이면 영원히 올라탄 채 멈추는 버그였는데, 코드만 읽어서는 AI가 먼저 찾지 못했을 것이다.
- 버그는 물리 계산보다 화면·입력과 만나는 경계에서 더 많이 나왔다(접힌 카드의 폭 0 → NaN, 포커스가 스페이스를 가로챔, 생성 중 콜백 누락). 코드 리뷰를 5번 반복해서 잡았다(16·8·6·6·3건).
- 직접 손으로 플레이해 본 것은 아니다. 구르는 느낌과 마찰·반발 값은 Playwright로 숫자를 재서 확인했을 뿐이라, 손맛에 맞춘 조정은 직접 해 보고 값을 바꿔야 할 수 있다.
- 화면에 보여 주는 코드(`impl.ts`)가 실제 코드의 복사본이라 코드를 고칠 때마다 어긋났고, 리뷰에서 가장 자주 지적됐다. 같은 내용을 두 곳에 두는 구조의 비용이다.
- 공이 수백 개로 늘면 공간 분할(격자)이나 Matter.js 같은 물리 라이브러리를 검토한다. 알려진 한계는 7번 참고.
