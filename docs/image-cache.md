# 이미지 캐싱 (Redis) 실험 노트

쇼핑몰처럼 "한시적으로 인기가 바뀌는 상품 이미지"를 어떻게 내려 주면 빠른지 비교한 노트.
구현은 `backend/image-service`(9205), 화면은 `frontend`의 "캐시 > 이미지 캐싱"(이미지 준비 / 캐시 실험 / 이미지 교체와 캐시 무효화).

## 1. 비교하는 방식

| mode | 요청이 올 때 서버가 하는 일 |
|---|---|
| `nocache` | 원본(1200x900)을 읽고, 요청 크기로 줄이고, JPEG으로 다시 인코딩 |
| `prebuilt` | 업로드할 때 줄여 둔 파일(웹 800x600 / 앱 400x300 / 썸네일 150x113)을 읽기만 함 |
| `redis` | Redis를 먼저 확인하고, 없을 때만 `prebuilt` 파일을 읽음. 최근 자주 찾는 것만 Redis에 올림 |

- `redis`는 `prebuilt` 위에 얹는 캐시 층이다. 그래서 `prebuilt`가 기준선이다.
- 원본 저장소가 로컬 디스크라서 너무 빠르기 때문에, 원격 스토리지(S3 등)를 흉내 내는 **원본 저장소 지연(ms)** 을 읽기마다 넣는다(기본 5ms).
- Redis 키는 `img:{상품}:v{버전}:{크기}`, "자주 본다" 카운터는 `hot:{실험}:{상품}:{크기}`(윈도 안에 기준 횟수 이상 캐시를 못 찾으면 Redis에 올린다).

## 2. 실험 조건 (화면에서 모두 바꿀 수 있다)

| 구분 | 값 |
|---|---|
| 부하 | 요청 수, 동시 스레드, 전체 상품 수, 원본 저장소 지연 |
| 인기 패턴 | 인기 상품 수, 인기 상품에 몰리는 비율(%), 인기 집합 교체 주기(요청 수마다 통째로 바뀜) |
| Redis | TTL, 올리는 기준 횟수, "자주"를 세는 윈도(초), 메모리 한도, 제거 정책(`allkeys-lfu`/`allkeys-lru`/`volatile-ttl`/`noeviction`), 동시 요청 합치기, 실험 전 캐시 비우기 |

요청은 웹 40% · 앱 40% · 썸네일 20%로 섞는다. 이미지는 "이미지 만들기"(서버가 직접 그림) 또는 "샘플 사진 받기"(picsum.photos 실제 사진)로 준비한다.

## 3. 측정 환경

- 이미지: 실제 사진 200장(원본 평균 약 135KB, 웹 약 70KB, 앱 약 25KB, 썸네일 약 7KB). 상품 200개 전부를 요청 대상으로 썼다.
- 공통 조건: 요청 10,000건, 스레드 16, 인기 상품 20개(80%), 5,000건마다 인기 집합 교체, 원본 지연 5ms, TTL 60초, 올리는 기준 2회/60초, 동시 요청 합치기 켬, Redis 128MB `allkeys-lfu`. 표에서 바꾼 값만 따로 적는다.
- Redis는 같은 PC의 컨테이너(redis:7-alpine), 서비스도 같은 PC에서 돌렸다. 네트워크 지연이 거의 없는 환경이다.
- 같은 조건을 1회씩만 쟀다(반복 측정 없음). 작은 차이(몇 %)는 의미를 두지 않는다.

## 4. 결과

### 4.1 방식 비교

| 방식 | 평균 | p95 | 처리량(건/초) | 적중률 | 원본 읽기 |
|---|---|---|---|---|---|
| `nocache` | 245.34ms | 347.15ms | 65 | - | 10,000 |
| `prebuilt` | 5.26ms | 5.46ms | 3,034 | - | 10,000 |
| `redis` | 1.08ms | 6.04ms | 14,666 | 88.4% | 1,080 |

- 리사이징을 요청마다 하면 사진 기준으로 245ms. 그림 이미지(작은 파일)로 쟀을 때 약 48ms였으니 **실제 사진은 리사이징 비용이 5배 정도 크다.**
- `prebuilt`의 5.26ms는 대부분 원본 지연 5ms이다. 파일 읽기 자체는 거의 공짜다.
- `redis`는 평균 1.08ms인데 p95가 6.04ms인 이유: 적중하면 1ms 미만, 못 찾은 12%는 원본(5ms)까지 가기 때문이다.

### 4.2 원본 저장소 지연에 따라 Redis의 이점이 어떻게 변하나

| 원본 지연 | `prebuilt` 평균 | `redis` 평균 | 적중률 |
|---|---|---|---|
| 0ms | **0.04ms** | 0.54ms | 88.6% |
| 5ms | 5.26ms | 0.75ms | 88.2% |
| 20ms | 20.27ms | 2.67ms | 88.2% |

- **원본이 빠르면 Redis가 오히려 느리다**(0ms: 0.04ms vs 0.54ms). Redis까지 네트워크 왕복과 바이트 전송이 로컬 파일 읽기보다 비싸다.
- 원본이 느릴수록 이점이 커진다(20ms에서 약 7.6배). 캐시의 가치는 "원본까지 가는 비용"이 결정한다.
- 즉 원본이 로컬 SSD 정도면 `prebuilt`로 충분하고, S3 같은 원격 저장소일 때 Redis가 의미 있다.

### 4.3 올리는 기준 횟수(윈도 안에 못 찾은 횟수)

| 기준 | 평균 | 적중률 | 원본 읽기 | Redis 메모리 |
|---|---|---|---|---|
| 1회 | 0.53ms | 93.9% | 571 | 21.0MB |
| 2회 | 0.81ms | 88.3% | 1,073 | 19.9MB |
| 5회 | 1.25ms | 78.2% | 1,993 | 10.6MB |

기준이 높을수록 "한 번 보고 마는" 이미지가 캐시에 안 올라 메모리가 절반으로 줄지만 적중률이 떨어진다. 이 실험은 상품이 200개뿐이라 메모리가 모자라지 않아서 1회가 가장 좋게 나왔다. 상품이 수십만 개로 늘어 메모리가 모자라는 상황이면 기준을 높이는 쪽이 유리해질 것이다(직접 재 보지 않음).

### 4.4 동시 요청 합치기 (스레드 32, 원본 지연 20ms)

| 합치기 | 평균 | 적중률 | 원본 읽기 |
|---|---|---|---|
| 켬 | 2.68ms | 87.3% | 1,044 |
| 끔 | 2.71ms | 87.7% | 1,234 |

원본 읽기가 약 15% 줄었지만 평균 응답은 차이가 없다. 인기 상품이 20개뿐이라 같은 이미지에 동시에 몰리는 일이 적었다. 이 기능은 "인기 상품 하나가 캐시에서 막 빠진 순간 수천 요청이 몰리는" 상황에서 의미가 있어서, 이 조건으로는 효과를 크게 못 봤다.

### 4.5 메모리 한도 6MB (이미지 전체는 약 20MB)

| 제거 정책 | 평균 | 적중률 | 제거된 키 | 원본 읽기 |
|---|---|---|---|---|
| `allkeys-lfu` | 1.30ms | 76.4% | 1,904 | 2,079 |
| `allkeys-lru` | 1.41ms | 73.5% | 1,848 | 2,194 |
| `noeviction` | 3.53ms | 47.3% | 0 | 4,692 |

- 메모리가 모자랄 때 `noeviction`은 먼저 올라간 이미지가 계속 자리를 차지해서, 인기 집합이 바뀐 뒤에도 새 인기 상품을 못 올린다(적중률 47%). 쓰기가 거절돼도 응답은 정상으로 나가야 하므로, 쓰기 실패는 "캐시에 못 올린 미스"로 처리했다.
- `lfu`와 `lru`는 차이가 작다(3%p). 인기 집합이 통째로 바뀌는 패턴이라 "오래 인기 있던 것"을 지키는 `lfu`의 이점이 더 크지 않았다.

### 4.6 인기 집합이 바뀌는 속도

| 교체 주기 | 평균 | 적중률 |
|---|---|---|
| 없음 | 0.70ms | 88.8% |
| 5,000건마다 | 0.74ms | 88.2% |
| 1,000건마다 | 0.93ms | 84.6% |

교체가 잦을수록 적중률이 떨어진다. 화면의 "적중률 추이" 그래프에서 교체 지점마다 적중률이 뚝 떨어졌다가 회복되는 모양이 보인다(예: 5,000건 주기 20,000건 실행에서 0.57, 0.63, 0.71로 하락 후 회복).

## 5. 이미지 교체와 캐시 무효화

상품 사진을 새로 올렸을 때 캐시의 옛 이미지를 어떻게 처리할지. 상품 50개(웹/앱/썸네일 3종 = 요청 150건), TTL 300초.

| 방식 | 옛 이미지가 나간 횟수 | 무효화 시간 | 지운 키 | 남은 옛 키 |
|---|---|---|---|---|
| 무효화 없음 | 150/150 (100%) | 0.05ms | 0 | 0 |
| 캐시 삭제(`purge`) | 0/150 (0%) | 24.85ms | 150 | 0 |
| 버전 키(`version`) | 0/150 (0%) | 0.78ms | 0 | 150 |

- **없음**: TTL(300초)이 끝날 때까지 100% 옛 이미지가 나간다. 가장 단순하지만 사용자 눈에 바로 보이는 문제다.
- **삭제**: 즉시 반영된다. 상품마다 Redis를 호출해야 해서 시간이 걸린다(150키에 약 25ms, 파이프라인으로 묶으면 줄일 수 있다). 이 실험에서는 보지 않았지만, 지우는 틈에 옛 이미지를 이미 읽은 요청이 다시 캐시에 올리는 경쟁이 생길 수 있다.
- **버전 키**: 키에 버전을 넣어 두고 이미지가 바뀌면 버전만 올린다. 즉시 반영되고 빠르지만(0.78ms), 옛 키 150개가 TTL로 사라질 때까지 메모리를 차지한다.
- 이 실험에서 버전은 서버 메모리의 맵(상품 메타데이터라고 가정)에 둔다. 실서비스에서는 DB 같은 곳에 있는 값이므로 그 조회 비용이 따로 든다.

## 6. 정리 / 느낀 점

- **캐시의 가치는 원본까지 가는 비용이 정한다.** 원본이 로컬 파일이면 Redis가 오히려 느렸고, 원격 저장소 지연이 20ms일 때 약 7배 빨랐다.
- 리사이징을 요청마다 하는 것은 실제 사진에서 245ms로 현실적이지 않다. 미리 줄여 두는 것(`prebuilt`)이 먼저이고, Redis는 그 위에 얹는 것이다.
- 인기 상품이 자주 바뀌는 쇼핑몰이면 "자주 보는 것만 올리는 기준"과 "제거 정책"이 적중률을 좌우한다. 적중률 하락과 회복을 그래프로 직접 볼 수 있었다.
- 이미지를 바꾸는 순간 캐시를 어떻게 할지(삭제 / 버전 키)는 따로 정해야 한다. 버전 키가 단순하고 빠른 대신 메모리를 더 쓴다.

## 7. 한계

- 반복 측정을 하지 않았고, 같은 PC에서 서비스, Redis, 부하 생성이 함께 돌았다. 절대 수치보다 방식 간 차이의 방향을 본다.
- 이미지는 상품 200개(실제 사진)이고 크기 종류가 3개뿐이다. 수십만 상품, 메모리 압박, 큰 이미지는 다르게 나올 수 있다.
- CDN, HTTP 캐시 헤더(`Cache-Control`/`ETag`), 브라우저/앱별 전용 이미지 크기는 다루지 않았다. 서비스용 주소(`GET /api/image/{id}`)는 있지만 화면에서 실험하지 않았다.
- 실험 도중 서비스용 주소로 요청이 오면 같은 Redis를 쓰기 때문에 측정이 흔들릴 수 있다.
