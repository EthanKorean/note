# RAG 검색 실험 노트

문서를 조각으로 잘라 벡터로 바꿔 두고, 질문과 가까운 조각을 찾는 "찾기" 단계를 청킹과 검색 방식별로 재서 비교한 노트.
구현은 `backend/rag-service`(9207), 화면은 `frontend`의 "AI > RAG 검색"(모델·문서 준비 / 시나리오로 따라 하기 / 직접 조건 바꿔 실행 / 평가 결과 / 질문해 보기). 모르는 용어는 "AI > AI 용어 정리" 화면에 있다.

## 1. 왜 하는가

- **문제 1**: AI 모델은 학습이 끝난 뒤에 생긴 내용과 우리 회사 내부 문서를 모른다.
- **문제 2**: 모르는 것을 물으면 "모른다"고 하지 않고 그럴듯하게 지어낸다(할루시네이션). 틀린 답을 믿고 업무에 쓰면 사고가 된다.
- **문제 3**: 문서를 통째로 넣으면 입력 한도, 비용, 속도가 나빠진다. 문서를 모델에게 다시 학습시키는 것은 더 비싸고 느리다.
- **해결**: 질문이 올 때 관련 있는 조각만 찾아 붙여 주는 RAG(Retrieval-Augmented Generation). 근거를 보여 줄 수 있고, 문서가 바뀌면 바로 반영된다.
- **핵심**: 답의 품질은 "정답이 든 조각을 찾아 오느냐"에 달려 있다. 못 찾으면 모델은 모르는 채로 지어낸다. 그래서 답을 쓰게 하기 전에 **찾기를 먼저 숫자로 잰다**.
- **업무 연결**: 사내 지식을 믿을 수 있게 답하는 일은 AX 과제에서 흔한 첫 주제다. 청킹이나 검색 방식을 바꿀 때 "좋아진 것 같다"가 아니라 같은 질문 세트의 점수로 말할 수 있어야 한다.

## 2. 파이프라인

```
문서(*.md) ──청킹──▶ 조각들 ──임베딩──▶ 벡터 ┐
                              └─ 단어 색인 ─┤  (색인: 청킹 조건마다 한 번 만든다)
질문 ──임베딩(query: )──▶ 질문 벡터 ──▶ 벡터 검색 ┐
질문 ──────────────────▶ 키워드 검색(BM25) ──────┼─▶ 상위 k개 조각
                                  하이브리드(RRF 로 순위 합침) ┘
(이 노트의 범위는 여기까지. 이후: 조각을 프롬프트에 붙여 모델이 답을 쓴다)
```

| 단계 | 이 프로젝트의 구현 |
|---|---|
| 청킹 | `Chunker`: 고정 길이 / 문단 / 제목 단위 |
| 임베딩 | `Embedder`: multilingual-e5-small(양자화 ONNX, 약 118MB)을 서비스 안에서 직접 실행. 토크나이저는 DJL(HuggingFace tokenizers). 입력 한도 512 토큰 |
| 벡터 검색 | `SearchIndex`: 메모리에서 전부 비교(조각이 수십~수백 개라 충분). 벡터를 길이 1로 정규화해서 내적이 곧 코사인 유사도 |
| 키워드 검색 | `Bm25`: 라이브러리 없이 공식을 직접 구현(k1=1.5, b=0.75). 한글은 통째로와 글자 2개 단위(bigram, 3글자 이상 단어만)를 함께 넣고 한 글자 조사는 뺀다 |
| 하이브리드 | `SearchIndex`: 두 검색의 상위 50개를 RRF(각 순위의 1/(60+순위) 합)로 합친다 |
| 평가 | `EvalRunner`: 질문 35개로 hit@1/3/5, MRR, 검색 시간을 잰다. 결과는 `test_result`(타입 `rag-eval`)에 저장 |

API(gateway 경유): `GET /api/rag/status`, `POST /api/rag/prepare`(모델 내려받기와 문서 읽기), `POST /api/rag/eval`, `GET /api/rag/search?q=...`. 진행 메시지는 STOMP(`/ws-rag`, `/topic/rag`). 평가, 질문 검색, 준비는 한 번에 하나만 실행된다(다른 작업이 돌고 있으면 409). 평가 중에 다른 검색이 끼어들면 시간 측정이 흔들리기 때문이다.

## 3. 실험 조건

- **문서**: 이 저장소의 `docs/` 바로 아래 `*.md` 인 `bulk-insert.md`, `image-cache.md`, `suika-game.md`, `README.md`(72자짜리 목차)의 4개(약 2만 자). **하위 폴더는 읽지 않는다.** 이 노트(`docs/ax/rag.md`)와 DB 락 노트(`docs/db/lock.md`)는 하위 폴더에 있어서 검색 대상이 아니다. 이 노트는 정답 문구를 그대로 담고 있어서, 말뭉치에 들어가면 평가가 순환하고 여기 적은 숫자를 화면에서 재현할 수 없게 된다. 새 노트가 `docs/` 바로 아래에 생겨도 숫자가 바뀐다.
- **질문**: 35개(`eval-questions.json`). 이미지 캐싱 17개, 대량 적재 10개, 수박 게임 8개.
- **정답 판정**: 조각 번호가 아니라 **정답 문구**로 적는다(예: `"47.3%"`). 조각이 그 문구를 모두 담고 있으면 정답 조각이다. 청킹 방식이 달라서 조각 번호가 달라져도 같은 질문 세트로 비교하려는 것이다. 문서가 바뀌어 문구를 못 찾는 질문은 화면에서 경고한다.
- **청킹**: 조각 크기 500자(고정 길이는 앞 조각과 50자 겹침)를 기본으로, 300자, 1,000자, 겹침 0·150자도 비교했다.
- **검색**: 벡터 / 키워드(BM25) / 하이브리드. 상위 5개를 본다.
- **지표**: hit@k = 정답 조각이 상위 k개에 있는 질문의 비율, MRR = 정답이 처음 나온 순위의 역수 평균(1등 1, 2등 0.5, 5등 안에 없으면 0). 시간은 질문 한 건 검색에 걸린 평균(질문을 벡터로 바꾸는 시간 포함, 색인 만드는 시간 제외, 측정 전에 3건을 먼저 돌려 JIT 영향을 뺀다).
- **재현성**: 같은 조건은 몇 번을 돌려도, 서비스를 다시 띄워도 같은 점수가 나온다(조건 14개 × 검색 3개 = 42개 값을 서비스를 다시 띄우고 순서를 거꾸로 해서 두 번 돌려 전부 같음을 확인). 임베딩을 글 하나씩 계산하기 때문이다(6장 참고).
- 같은 PC에서 서비스, DB, 브라우저가 함께 돌았다. 시간은 1회씩만 쟀다.

화면의 "시나리오로 따라 하기"는 아래 4.1 ~ 4.5의 실험(조건 14개)을 순서대로 버튼으로 돌려 볼 수 있게 만든 것이다. 시나리오마다 왜 하는지, 무엇을 볼지, 내 PC에서의 값을 적어 뒀다.

## 4. 결과

### 4.1 청킹 × 검색 (조각 500자)

| 청킹 | 검색 | MRR | hit@1 | hit@3 | hit@5 | 평균 시간 | 놓친 질문 |
|---|---|---|---|---|---|---|---|
| 고정 길이 (조각 48개) | 벡터 | 0.647 | 51.4% | 74.3% | 88.6% | 3.26ms | 4 |
|  | 키워드 | 0.739 | 62.9% | 82.9% | 91.4% | 0.05ms | 3 |
|  | 하이브리드 | 0.714 | 57.1% | 88.6% | 94.3% | 3.28ms | 2 |
| 문단 (조각 48개) | 벡터 | 0.678 | 54.3% | 80.0% | 85.7% | 3.23ms | 5 |
|  | 키워드 | 0.747 | 65.7% | 82.9% | 91.4% | 0.06ms | 3 |
|  | 하이브리드 | 0.742 | 62.9% | 82.9% | 91.4% | 3.18ms | 3 |
| **제목 단위 (조각 57개)** | 벡터 | 0.745 | 62.9% | 88.6% | 94.3% | 3.11ms | 2 |
|  | 키워드 | 0.752 | 68.6% | 82.9% | 82.9% | 0.03ms | 6 |
|  | **하이브리드** | **0.810** | **74.3%** | 85.7% | 94.3% | 3.23ms | 2 |

- 500자에서는 **제목 단위 + 하이브리드가 가장 좋았다**(MRR 0.810).
- 같은 검색 방식에서 청킹만 바꿔도 MRR이 움직였다(벡터: 고정 0.647, 문단 0.678, 제목 0.745).
- 제목 단위는 조각 앞에 "파일 > 제목"을 붙여 검색하기 때문에, 질문에 제목과 겹치는 말이 있으면 유리했을 것이다(직접 분리해서 검증하지는 않았다).
- 고정 길이와 문단에서는 하이브리드가 키워드 단독보다 오히려 낮았다. 합치면 항상 좋아지는 것은 아니다.

### 4.2 조각 크기에 따른 MRR (고정 길이는 겹침 50자)

| 청킹 | 검색 | 300자 | 500자 | 1,000자 |
|---|---|---|---|---|
| 고정 길이 (조각 84 / 48 / 24개) | 벡터 | 0.614 | 0.647 | 0.674 |
|  | 키워드 | 0.668 | 0.739 | 0.799 |
|  | 하이브리드 | 0.608 | 0.714 | 0.787 |
| 문단 (조각 68 / 48 / 26개) | 벡터 | 0.652 | 0.678 | 0.739 |
|  | 키워드 | 0.642 | 0.747 | **0.849** |
|  | 하이브리드 | 0.683 | 0.742 | 0.810 |
| 제목 단위 (조각 75 / 57 / 48개) | 벡터 | 0.734 | 0.745 | 0.771 |
|  | 키워드 | 0.683 | 0.752 | 0.810 |
|  | 하이브리드 | 0.728 | 0.810 | 0.840 |

벡터가 뒤쪽이 잘린 채 만들어진 조각 수(512 토큰 초과): 1,000자에서 고정 길이 24개 중 19개 · 문단 26개 중 10개 · 제목 단위 48개 중 5개. 300·500자는 0~2개.

- 이 문서들에서는 **조각이 클수록 점수가 올라가는 경향**이 있었다. 하지만 이것을 "큰 조각이 더 좋은 검색"으로 읽으면 안 된다. 이 평가는 "정답 문구가 조각 안에 있느냐"만 보므로 **큰 조각에 구조적으로 유리하다**. 큰 조각은 모델에게 넘기는 글이 늘어난다(상위 5개 기준 제목 단위 500자는 약 1,800자, 고정 길이 3,000자는 약 11,500자).
- 벡터는 1,000자에서 조각 대부분이 앞부분만 반영됐으므로(4.5 참고), 키워드(조각 전체를 봄)와의 차이가 벌어진 데는 이 영향이 있을 것이다.
- 하이브리드가 키워드 단독보다 높았던 경우는 9개 조건 중 4개(제목 단위 세 크기와 문단 300자)였다. 고정 길이는 세 크기 모두, 문단 500·1,000자에서는 키워드 단독이 앞섰다.
- 표에서 가장 높은 값은 문단 + 키워드 1,000자(0.849)다. 제목 단위 + 하이브리드는 1,000자 0.840, 500자 0.810으로 그다음이다. 0.849와 0.840은 작은 차이라 우열을 말하지 않는다. 다만 "하이브리드가 가장 좋다"고 하기는 어렵다.

### 4.3 고정 길이의 겹침 (조각 500자)

| 겹침 | 조각 수 | 벡터 MRR | 키워드 MRR | 하이브리드 MRR | 정답이 잘려 어디에도 없는 질문 |
|---|---|---|---|---|---|
| 0자 | 44 | 0.653 | **0.769** | 0.763 | 1 |
| 50자 | 48 | 0.647 | 0.739 | 0.714 | 0 |
| 150자 | 60 | 0.621 | 0.732 | 0.730 | 0 |

- 겹침을 두면 조각 경계에서 정답이 잘리는 일은 줄었다(겹침 0자일 때 질문 1개의 정답이 두 조각으로 쪼개져 어디에도 통째로 없었다).
- 그런데 점수는 오히려 겹침이 없을 때 가장 높았다. 겹침이 늘수록 조각 수가 늘고 같은 내용이 여러 조각에 중복되어, 정답 조각이 상위 5개를 나눠 차지하며 순위를 밀어냈을 가능성이 있다(확인하지 않은 추측).

### 4.4 시간

- 키워드 검색은 **0.01 ~ 0.06ms**, 벡터는 **약 3.0 ~ 3.7ms**, 하이브리드는 **약 3.1 ~ 3.8ms**였다. 차이의 거의 전부가 질문을 벡터로 바꾸는 시간이다(하이브리드 = 벡터 + 키워드).
- 조각이 수십 개라서 조각 전체를 비교하는 시간은 사실상 0이다. 조각이 수십만 개로 늘면 벡터 비교 비용이 커져 벡터 DB(근사 검색 색인)가 필요해질 것이다(이번에는 재 보지 않음).
- 색인 만들기(조각 임베딩)는 조각 57개에 수 초였다. 같은 글은 다시 임베딩하지 않고 캐시하므로 색인 시간은 조건끼리 비교하지 않는다(화면에도 싣지 않는다).

### 4.5 조각이 너무 길면 벡터가 앞부분만 본다 (고정 길이, 겹침 0)

임베딩 모델의 입력 한도는 512 토큰이다. 조각이 이보다 길면 뒤쪽이 잘려서 벡터에 반영되지 않는다.

| 조각 크기 | 조각 수 | 평균 글자 | 뒤가 잘린 조각 | 벡터 MRR | 키워드 MRR | 하이브리드 MRR | 키워드 hit@5 |
|---|---|---|---|---|---|---|---|
| 1,000자 | 24 | 864 | **19** | 0.664 | 0.787 | 0.749 | 94.3% |
| 2,000자 | 13 | 1,596 | **11** | 0.643 | 0.840 | 0.836 | 97.1% |
| 3,000자 | 9 | 2,305 | **8** | 0.696 | 0.910 | 0.836 | 100.0% |

- 한국어는 이 모델에서 약 1.7자가 1토큰이라, 800~900자부터 잘리기 시작한다(표와 코드가 섞인 문서의 대략값).
- 조각이 커질수록 키워드 점수만 계속 오른다. **hit@5 100%는 좋은 검색이라는 뜻이 아니다.** 조각이 9개뿐이라 상위 5개를 주면 문서 전체의 절반이 넘는다. 이 지표만 보고 큰 조각을 고르면 모델에게 거의 문서 전체를 넘기게 된다.

## 5. 정리 / 느낀 점

- **찾기의 품질은 청킹으로 크게 달라진다.** 같은 검색 방식(벡터)에서 청킹만 바꿨을 뿐인데 MRR이 0.647 ~ 0.745로 움직였다. 모델을 바꾸기 전에 청킹부터 확인할 가치가 있다.
- **문서 구조를 따라 자르는 것(제목 단위)이 기계적으로 자르는 것보다 안정적이었다.** 조각이 한 주제에 묶여 있고 제목이 검색에 도움이 된다.
- **"하이브리드가 제일 좋다"는 말을 그대로 믿으면 안 된다.** 청킹과 조각 크기에 따라 키워드 단독이 이기기도 했다. 내 문서와 내 질문으로 재 봐야 안다.
- **점수만 보고 고르면 안 된다.** 큰 조각이 점수가 높게 나오는 것은 지표가 큰 조각에 유리하기 때문일 수 있다. 점수와 함께 "모델에게 넘기는 글의 양"과 "입력 한도에 잘리는 조각 수"를 같이 봐야 한다.
- **측정 도구도 검증해야 한다.** 이번 실험에서 측정 자체의 문제를 여섯 번 바로잡았다(6장).
- 지금은 찾기까지만 했다. 다음에는 찾은 조각을 모델에게 주고 답을 쓰게 한 뒤, 문서에 없는 질문에 "모른다"고 답하는지(할루시네이션)를 확인한다. "질문해 보기"에서 문서에 없는 질문을 넣어 보면, 검색은 못 찾았다는 신호 없이 "가장 가까운 것"을 돌려준다. 이 때문에 답변 단계에서 근거가 약하면 모른다고 하도록 막아야 한다.

## 6. 만들면서 막힌 점 (측정 도구의 문제 6가지)

1. **평가 대상에 이 노트가 섞였다.** 이 문서(`rag.md`)를 `docs/`에 만들자 검색 대상이 되어 조각 수가 57개에서 78개로 늘었다. 이 노트에는 질문의 정답 문구가 그대로 있어서 평가가 순환하고, 노트에 적은 숫자를 화면에서 재현할 수 없었다. 처음에는 파일 이름으로 뺐다가(`rag.docs-exclude`), 나중에 노트를 `docs/ax/` 하위 폴더로 옮겨 말뭉치와 분리했다. 옮긴 뒤 조각 수와 점수가 노트의 값과 같아지는 것을 확인했다.
2. **질문 임베딩을 캐시했더니 벡터 검색 시간이 틀렸다.** 두 번째 평가부터 벡터 검색 시간이 0.03ms로 나왔다(첫 평가는 3.5ms). 질문 임베딩은 캐시하지 않게 고쳤다. 시간을 비교하는 실험에서 캐시가 숨어 있으면 안 된다. 첫 몇 번의 검색은 JIT 때문에 느려서, 측정 전에 3건을 먼저 돌려 둔다.
3. **같은 조건인데 점수가 달랐다.** 여러 글을 한 번에 묶어 임베딩하면 가장 긴 글에 맞춰 패딩이 붙는데, 양자화 모델은 패딩 길이에 따라 결과가 미세하게 달라진다. 캐시 상태에 따라 묶음이 달라져서 같은 조건의 MRR이 0.02 ~ 0.03 흔들렸다(예: 고정 1,000자 벡터 0.705 vs 0.729). 글 하나씩 계산하게 바꾸자 순서와 캐시 상태를 바꿔도 33개 값이 전부 같아졌다. 이 노트의 표는 모두 고친 뒤의 값이다.
4. **잘린 조각을 세려다 0이 나왔다.** 토크나이저의 "넘친 부분(overflowing)" 값으로 세었더니 3,000자 조각에서도 0이었다(실제로는 대부분 잘림). 토큰 수가 한도(512)에 꽉 찼는지로 직접 세도록 바꿨다.
5. **키워드 검색이 두 글자 단어를 두 번 셌다.** 한글은 단어 통째와 글자 2개 단위로 함께 넣는데, 두 글자 단어는 둘이 같은 글자라서 한 번 나온 단어가 두 번으로 집계됐다("적중", "캐시" 같은 짧은 명사). 코드 리뷰에서 발견했고, 세 글자부터 쪼개도록 고쳐 다시 쟀다. 키워드와 하이브리드 값이 바뀌었다(예: 제목 단위 하이브리드 0.826 → 0.846). 벡터 값과 조각 수는 그대로다.
6. **한 글자 조사가 점수에 잡음을 더했다.** "Redis에"처럼 영문 단어에 붙은 조사 "에" 같은 한 글자 한글이 거의 모든 조각에 나와서 키워드 점수에 잡음이 됐다. 한 글자 한글은 뺐다(코드 리뷰에서 발견). 값이 한 번 더 바뀌었다(예: 제목 단위 하이브리드 0.846 → 0.810). 벡터 값은 그대로다. **이 노트의 표는 모두 마지막으로 고친 뒤의 값이다.** 같은 시기에 잘림 감지도 "정확히 512 토큰"을 잘린 것으로 세던 문제가 있어서 토크나이저에 맡기지 않고 직접 자르는 방식으로 바꿨다(벡터 값과 잘림 수는 그대로).

## 7. 한계

- **질문이 35개뿐이다.** 질문 하나가 2.9%p다. 몇 % 차이는 의미를 두지 않는다. 시간은 1회씩만 쟀다.
- **질문을 내가 문서를 보면서 만들었다.** 질문에 문서의 단어가 그대로 들어 있어서 키워드 검색에 유리하고, 뜻 기반 검색의 장점(다른 말로 물어도 찾기)은 덜 드러났을 수 있다. 사용자가 실제로 하는 질문은 더 다양한 표현을 쓴다.
- **hit@k와 MRR은 큰 조각에 유리하다.** 정답 문구가 조각 안에 있기만 하면 정답으로 센다. 조각이 크면 모델에게 넘기는 글이 늘고 불필요한 내용이 섞이는데, 이 지표는 그 대가를 반영하지 않는다.
- **정답 문구가 다른 조각에도 나오면 그 조각도 정답으로 센다.** 예를 들어 "2,849"는 여러 곳에 있다. 정답 문구를 되도록 한곳에만 있는 것으로 골랐지만 완전히 막지는 못했다.
- **벡터는 조각의 앞 512 토큰만 본다.** 긴 조각을 쓴 결과의 벡터 점수는 "뜻 검색의 한계"가 아니라 "잘린 입력"의 영향일 수 있다. 화면에 "뒤가 잘린 조각" 수를 표시하지만, 잘림을 없앤 상태(긴 조각을 나눠 임베딩해 합치는 방식)와는 비교하지 않았다.
- 문서는 약 2만 자, 모두 한국어 마크다운이다. PDF, 표가 깨진 텍스트, 수십만 조각의 규모는 다르게 나올 수 있다.
- 임베딩 모델은 양자화된 multilingual-e5-small 하나만 썼다. 원본(양자화 전)이나 더 큰 모델과는 비교하지 않았다. 한국어 키워드 분리는 글자 2개 단위(bigram)를 쓰는 단순한 방식이다.
- 리랭커, 벡터 DB(pgvector, Redis 등) 비교는 하지 않았다.
- 문서(`docs/*.md`)를 고치면 정답 문구가 사라질 수 있다. 화면의 "모델·문서 준비" 카드가 찾을 수 없는 질문을 알려 준다.
